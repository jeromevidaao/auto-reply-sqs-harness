## Core Product
Local-first evaluation harness + core agent logic for the Grok-powered guest messaging / auto-reply system (originally the `auto-reply-sqs` Lambda).

- Hospitable **message POST** is rate-limited (**2/min per reservation**, 50/5 min global). GET `/reservations/{id}/messages` shares a similarly tight window (`Retry-After` ~50–60s). Two-layer retry: in-Lambda **4 attempts / ~3 min** (20s timeout, exp backoff, min 30s between POSTs, GET-confirm after timeout); then SQS `grok_message` **4 receives / 12 min visibility (~36–40 min)** then `grok_message_dl`. Constants in `src/utils/httpRetry.js`. Queue attrs + Lambda timeout 360s are out-of-band (deploy role cannot `UpdateFunctionConfiguration`).
- **Per-reservation lock** (`src/utils/reservationLock.js`, Dynamo `airbnb-harness-dedup` key `lock:resv:{id}`): standard `grok_message` is not FIFO. Rapid guest messages on the **same** reservation must not run two Lambdas (Carlos 2026-08-28 — first invoke 65796ac5 held the lock ~131s; sibling 300ed18e waited 88s, timed out, proceeded, second “You're welcome”). **Do not wait.** If the lock is held, return 200 so SQS **deletes** that message. The in-flight handler GETs the live thread immediately before POST (`runPreSendThreadRefresh`, always GET) and re-runs first-pass + judge with the original + newer guest turns as one reply. After a **200 POST**, do **not** GET again to verify. Parallel invokes on **different** reservations/conversations are fine. TTL 420s (outlasts Lambda 360s).
- The "brain" (prompts + agent multipass pipeline + tools + evals) lives here.
- Real guest conversations (from Hospitable/Airbnb) are first-class test data.
- Changes are iterated locally with `npm test`, `npm run simulate`, `npm run eval`.
- Production deployment of the Lambda (`guest-messaging-agent-harness`) is **automatic on push to main** via `.github/workflows/deploy.yml` (builds zip from src/ + prompts/ + lambda/ + node_modules and calls update-function-code).
- **Commit → push = the deployment mechanism**. Never edit production directly.

## Mandatory Process for ANY Code or Doc Change
1. Make the edit(s).
2. **HARD prepush (do this before `git push`, not after CI is red):** `npm run prepush` (or `python3 ~/.grok/skills/guest-messaging-harness/scripts/prepush.py` so `GROK_API_KEY` is loaded from SSM `/grok/api-key`). That runs phrase/snippet sync, `npm test`, targeted live eval for changed goldens, then the **full** live suite with **no** `--fail-fast`. Skip the live Grok steps only for docs/tooling-only diffs. **Do not push if prepush is red.** Skill: `guest-messaging-harness`.
   - **Harden every CI fail permanently.** If CI eval/test fails, pull the log, fix locally, and **re-run the exact failing eval/test locally until green before the next push** (e.g. `npm run eval -- --only=jane-tv-wifi-connect`). Never push hoping CI will be luckier.
   - **Credential / WiFi / prompt policy changes:** when SSID/password resolution, placeholders, or hostContacts change, update **all** goldens/scenarios that assert SSID/password phrases in the **same PR** (grep `requiredPhrases` / goldens for `WIFI_SSID`, `WRONG_SSID`, `Pineland`, `non-canonical`, etc.). CI 35292706988 failed because Pine template WiFi shipped while `jane-tv-wifi-connect` still required `WRONG_SSID`.
3. `git add -A`
4. `git commit -m "Clear message describing the change and why (e.g. the user request or bug)."`
5. Make the repo **public**, then `git push`. Watch CI green, then make it **private** again.
6. `git status` — must be clean.
7. Verify the remote at the exact new SHA using the GitHub MCP tools (get_file_contents on the key files you edited, at the commit SHA on main branch of jeromevidaao/auto-reply-sqs-harness).
8. Only after the above is the change "done".

This rule exists because the harness directly affects live guest replies and the Lambda is auto-deployed from main. Skipping hygiene has caused production drift in the past. CI eval must not be the first time new `requiredPhrases` are tested.
